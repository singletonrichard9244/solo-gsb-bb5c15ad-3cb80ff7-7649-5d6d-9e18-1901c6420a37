# 多通道传感器故障规则 Web 应用

本地运行的多通道传感器故障规则工作台：导入 JSONL 遥测事件 → 定义带 AND/OR 与持续时长的故障规则 →
把每个通道的样本值展开为**半开时间区间** `[start, end)`，用**扫描线（sweep line）**合并条件真值，
产出每条规则的**故障区间**及**触发证据** → 在时间轴上创建区间标注 → 按时间范围筛选并导出包含
原始事件、故障区间、故障事件、规则与证据的 JSON。故障列表旁提供**故障事件**视图：不同规则产生、
时间区间重叠或首尾相接（含传递链）的故障归并为同一事件。

页面还提供只读的**规则组合故障日账**：勾选一组规则并给出 UTC 查询时间范围，读取这些规则
**已保存的故障区间**，先按半开区间合并重叠或相接片段（多规则同时故障只计一次），再按
**UTC 午夜**切分，逐日给出去重故障秒数、新起片段数、跨日延续片段数与故障覆盖率；日账只读取
现有已确认故障结果，不触发重算（规则变更后的重算仍由导入 / 有效期 / 维护等现有流程负责）。

每个通道（设备 + 指标）还可单独配置**采样有效期（TTL，正秒数）**：样本值只保持在
`[采样时刻, min(下一样本时刻, 采样时刻+有效期, 数据终点))`；到期后的空档不满足该通道任何条件，
AND/OR 按各通道有效片段组合，规则真值中断后持续时长重新累计，故障区间、确认时刻与触发证据都不
跨越空档。未配置有效期的通道沿用「保持到下一样本（末样本保持到数据终点）」语义。在页面和 API
中均可查看、设置、清除有效期；变更有效期或补传旧时间样本都会自动重算已存故障。

内置**计划维护**能力：按设备创建带名称的半开维护窗口 `[start, end)`；评估规则时先把同设备
重叠或相接的维护窗口合并，再从该设备参与规则形成的真值段中**扣除**——维护造成的中断会
**重置持续时长**，窗口结束后重新累计并生成新的确认时刻；被扣除的片段作为**被抑制片段**
与维护带一起展示在时间轴上，并随导出 JSON 一并输出。

条件还可设置可选的**复位阈值（迟滞）**：仅 `>`、`>=`、`<`、`<=` 条件可配置，高值触发时
复位阈值必须低于触发阈值、低值触发时必须高于。首次满足原比较才进入命中，此后即使样本值
在触发阈值附近波动也保持命中，直到样本值到达复位边界（高值触发 `值 ≤ 复位值`、低值触发
`值 ≥ 复位值`）才解除；采样有效期到期产生空档同样清除命中状态。以此减少阈值附近抖动造成的
故障碎片，且 AND/OR、持续时长、维护扣除与证据沿用同一套评估链。

页面侧栏提供**导入批次撤销**：文件或文本导入时，服务端会为本批**首次遇到**的每个
（设备、指标、时间戳）键记录一条**导入前快照**——同批重复键只快照一次（仍由最后一条有效值
覆盖），覆盖到旧事件时把旧值、原始内容与原批次归属一并存档。「导入批次 / 撤销」卡片列出
全部批次；仅**最近一次未撤销**且快照完整的批次显示「撤销本批」入口。撤销在**同一事务**中
删除本批新增事件、把被覆盖事件恢复为原值 / 原内容 / 原批次归属，并把批次标记为已撤销，
任一步失败全部回滚；成功后沿用现有评估流程刷新故障，提示删除与恢复数量。旧版本数据中
**无快照的批次会被明确拒绝**（409），不能撤销。「清空数据」会同步清除全部快照。

技术栈：Python 3.11 · FastAPI · SQLite（标准库 `sqlite3`）· 原生 JavaScript（无构建、无前端框架）。

## 一条命令启动（推荐 Docker Compose）

```bash
docker compose up --build
```

启动后访问：

- **地址 / 端口：http://localhost:8000**
- API 文档（Swagger UI）：http://localhost:8000/docs
- 健康检查：http://localhost:8000/api/health

数据保存在 Docker 卷 `sensor-data` 内的 SQLite 文件 `/data/sensor.db`，容器重启不丢失。
停止用 `docker compose down`；连数据卷一起删除用 `docker compose down -v`。

### 不用 Compose（仅 Docker）

```bash
docker build -t sensor-fault-rules .
docker run --rm -p 8000:8000 -v "$PWD/data:/data" sensor-fault-rules
# 打开 http://localhost:8000
```

### 不用 Docker（本机 Python 3.11+）

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 打开 http://localhost:8000
```

本机运行时数据库默认位于仓库下 `data/sensor.db`（可用环境变量 `SENSOR_DB_PATH` 覆盖）。

## 快速体验

1. 打开 http://localhost:8000 ，点击顶部 **「载入示例」**，自动导入 `samples/telemetry.jsonl`
   （4 个通道、31 分钟、每分钟一个点）并创建 3 条示例规则。
2. 点击 **「评估规则」**，时间轴和故障列表会显示 4 个故障区间：
   - `pump-1 高温持续`：temp ≥ 80 且持续 ≥ 5 分钟 → `[00:06, 00:17)`；`00:20` 的单点尖峰被持续时长过滤；
   - `pump-1 高温且振动`（AND，2 分钟）→ `[00:12, 00:14)`；
   - `pump-2 振动大或压力低`（OR，200 秒）：vib>5 的 `[00:03,00:06)` 与 press<30 的
     `[00:06,00:09)` **在 00:06 边界相接，按连续处理**，合并为单个故障 `[00:03,00:09)`；
     另一个独立的压力低谷 `[00:10,00:14)` 为第二个故障。
3. 切到故障卡片右上角的 **「故障事件」** 标签：上述 4 个故障经传递归并为 **1 个事件**
   `[00:03, 00:17)`——pump-2 的 `[00:03,00:09)` 与 pump-1 高温的 `[00:06,00:17)` 首尾相接，
   后者又与 `[00:10,00:14)`、`[00:12,00:14)` 重叠。点击事件可展开成员规则、各自半开区间与原触发证据。
4. 在时间轴上**按住拖拽**框选一段时间，填写名称即可创建区间标注；框选弹层里切换到
   **「维护窗口」** 并填写设备，即可直接创建计划维护窗口。
5. 点击故障色块或故障行，展开每个条件的触发样本证据；再点 **「导出 JSON」** 下载完整结果。
6. 编辑（或新建）规则时先点 **「预览影响」**：不保存即可看到草稿相对原规则的已确认故障
   **新增 / 消失片段**，以及**区间没变但确认时刻移动**的重叠片段；没有任何差异时显示「无变化」。
   预览只读，确认后再点「保存」走原流程。

### 试试采样有效期（TTL）

1. 在左侧 **「采样有效期」** 卡片点 **「设置」**（或泳道徽标），为 `pump-1` / `temp` 填
   `45` 秒保存。保存后**自动重新评估**全部规则。
2. 对比评估结果：该通道样本每分钟一个，45 秒后样本值失效，每个高温点只持有 `[t, t+45s)`，
   空档不满足条件；`pump-1 高温持续`（需 5 分钟）与 `pump-1 高温且振动`（AND）因此都消失，
   pump-2 两条规则不受影响。时间轴对应泳道左上角出现紫色 **⏳ 有效期** 徽标，悬停可见语义。
3. 把有效期改为 `60` 秒：持有段恰好在下一样本时刻首尾相接，按半开区间连续处理，故障恢复；
   改为 `90` 秒也同样连续（样本在有效期内就被新样本接管）。点编辑弹层里的 **「清除有效期」**
   （或列表行的 ✕）即恢复为默认「保持到下一样本」语义并再次自动重算。

### 试试计划维护

1. 在左侧 **「计划维护」** 卡片点击 **「新建」**（或在时间轴拖拽框选后选「维护窗口」），创建
   设备 `pump-1`、名称任意、`2026-09-23 00:10:00Z ~ 00:12:00Z` 的窗口。保存后**自动重新评估**全部规则。
2. 对比评估结果：`pump-1 高温持续` 原本 `[00:06,00:17)` 的故障被维护窗口切断——
   `[00:06,00:10)` 只剩 4 分钟、不足 5 分钟持续时长而消失；`[00:12,00:17)` 从窗口结束处
   **重新累计**，于 `00:17`（= 00:12 + 5 分钟）再次确认。`pump-1 高温且振动` 的 `[00:12,00:14)`
   恰好从维护结束处开始，不受影响。
3. 时间轴顶部出现青色**维护带**，pump-1 各泳道内同时渲染维护底色；被扣除的
   `[00:10,00:12)` 片段以琥珀色斜纹**被抑制片段**显示在对应泳道顶部，悬停可见关联的规则与维护窗口。
4. 删除该维护窗口后再次自动评估，故障区间恢复为原来的 4 个。

### 试试复位阈值（迟滞）

1. 新建（或编辑）规则，添加条件 `pump-2` / `vib` `>` `5`，在同行的**「复位阈值」**框填
   `4`（必须低于触发阈值），保存后点 **「评估规则」**：样本在 5 附近来回波动、一度跌到
   `4~5` 之间时不会再把故障切成碎片；只有值跌到 `≤ 4` 才解除，再次 `> 5` 才重新命中。
   规则徽标会以青色「（复位 4）」标出，时间轴对应泳道在触发线下方多一条同色**虚线**复位边界。
2. 编辑条件把运算符改成 `==` 或 `!=`：复位阈值框自动禁用并清空（这两类条件不支持复位）。
   直接保存不合法组合（如高值触发但复位值 ≥ 触发值）会被前后端拒绝并提示原因。
3. 把复位阈值框**清空**再保存即恢复为原比较；编辑时也可随时点 **「预览影响」**，草稿设置的
   复位阈值同样参与即时试算（不落库），可先看到原本抖动碎片被合并后的新增/消失片段再保存。
4. 若该通道同时配置了**采样有效期**，到期空档会清除命中状态：空档之后处于迟滞带内的样本
   不会自行恢复命中，必须等再次满足原比较的样本出现。

### 试试撤销导入批次

1. 连续导入两次（可在顶部 **「导入 JSONL」** 面板粘贴文本或选文件）：第一批写若干事件，
   第二批覆盖其中部分键、再新增部分键。
2. 在左侧 **「导入批次 / 撤销」** 卡片查看批次列表：每批显示新增 / 覆盖 / 跳过行数与
   快照键数；只有**最新一批**带蓝色「可撤销（最近一次）」标记和 **「撤销本批」** 按钮，
   较早的批次标注「仅允许撤销最近一次未撤销的导入批次」，升级前导入的旧批次标注
   「旧批次缺少导入前快照，无法撤销」且无撤销入口。
3. 点最新批次的 **「撤销本批」** 并确认：本批新增的事件被删除、被它覆盖的事件恢复为原值、
   原始内容和原批次归属；随后自动重算故障，提示形如「删除 N 条新增事件，恢复 M 条覆盖事件」。
   同一批内同一（设备、指标、时间戳）出现多次时，快照只记首次遇到前的状态，撤销恢复的是
   该批导入前的值。
4. 撤销后该批次显示「已撤销」，其前一批自动成为可撤销批次（后进先出）。撤销过程任一步失败
   都会整体回滚，数据保持撤销前状态。
5. 点顶部 **「清空数据」** 会连同所有批次快照一起清除（页面入口仍为
   http://localhost:8000 顶部工具栏）。

### 试试规则组合故障日账

1. 「评估规则」后下滚到 **「规则组合故障日账」** 卡片，勾选全部 3 条示例规则，时间范围填
   `2026-09-23 00:00:00 ~ 2026-09-24 00:00`（按本机时区输入，按 UTC 查询），点 **「查询日账」**。
2. 逐日表格显示 `2026-09-23`：多条规则重叠 / 相接的故障（`[00:03, 00:17)` 一带）先合并为
   **1 个去重片段**（`新起片段 1`），故障秒数按合并后的并集计算，而不是把 4 个原始故障时长相加；
   覆盖率分母为当日实际查询秒数（整日 86400 秒）。无故障的日子也会列出（全 0）。
3. 把结束时间改到日中（如 `2026-09-23 12:00:00`）再查：首尾落在日中时，当日查询秒数变为
   43200，覆盖率相应重算；表格末行给出整个范围的合计。日账为**只读**视图——改规则、改时间范围
   都不会重算或修改已确认故障，需要新结果时点顶部「评估规则」或走导入 / 有效期 / 维护流程。

重新生成示例数据：`python3 samples/generate_sample.py`

## 数据模型与 JSONL 格式

每行一个 JSON 对象（JSONL），也接受 JSON 数组（`.json` 或直接粘贴）。默认字段：

```json
{"device": "pump-1", "metric": "temp", "ts": "2026-09-23T00:00:00Z", "value": 81.2}
```

- `device` 设备标识，`metric` 指标名（二者共同确定一个**通道**）。
- `ts` 时间戳：ISO-8601（推荐带 `Z`/时区，无时区按 UTC 处理）或 epoch（秒 / 毫秒，数字或数字字符串均可）。
- `value` 指标值：数字（非数字行会被跳过并计数）。
- 也支持**嵌套指标**对象，自动展开为每个键一条事件：
  `{"device":"pump-1","ts":"...","value":{"temp":81,"vib":2.1}}`。
- 字段名不同可在「字段映射」里自定义（如 `host/k/t/x`）。
- 同一 `(device, metric, ts)` 重复导入时**后值覆盖**。

## 故障规则

```
规则 = 条件列表 + 组合逻辑(AND|OR) + 持续时长(秒, ≥0)
条件 = 设备 + 指标 + 运算符(> >= < <= == !=) + 数值阈值 [+ 可选复位阈值]
```

- 每个通道的样本值在相邻两个样本之间保持：样本 `(tᵢ, vᵢ)` 持有于半开区间 `[tᵢ, tᵢ₊₁)`；
  通道最后一个样本持有到**全数据集最大时间戳**（horizon）。
- **复位阈值（可选，迟滞）**：仅 `>`、`>=`、`<`、`<=` 四个比较条件可设置；未设置时完全
  沿用原比较。设置后条件按**样本持有区间顺序**成为一个带记忆的锁存谓词：
  - 首次必须有一个持有值**满足原比较**才进入命中（处在触发阈值与复位阈值之间的“迟滞带”
    内的样本不会单独触发）；
  - 命中后即使持有值跌/升回触发阈值另一侧、但尚未到达复位边界，条件**仍然保持命中**，
    原本会被抖动切碎的真值段因此合并为一段连续区间；
  - 直到某个样本值**到达复位边界**才解除命中：**高值触发**（`>`/`>=`）时 `值 ≤ 复位值`
    解除，**低值触发**（`<`/`<=`）时 `值 ≥ 复位值` 解除；边界取等号即解除；
    此后需要重新满足原比较才能再次命中；
  - 复位阈值必须严格位于复位侧：高值触发复位值**低于**触发阈值，低值触发复位值**高于**
    触发阈值；`==`、`!=` 条件不支持复位阈值；
  - **采样有效期到期产生空档会清除命中状态**：空档之后即使下一样本仍在迟滞带内也不会命中，
    必须由重新满足原比较的样本再次触发；持有片段首尾相接（无空档）时锁存状态跨边界延续。
  - 复位阈值只改变“该条件通道在哪些持有区间为真”，其输出仍是普通半开区间：后续 **AND/OR
    组合、持续时长过滤（含空档/维护后的重新累计）、维护扣除与被抑制片段、逐条件证据**全部
    沿用现有评估链；锁存合并出的成立区间内，触发样本与迟滞带内保持命中的样本都作为证据。
- **采样有效期（TTL，可选）**：按 `(设备, 指标)` 配置正秒数 `s` 后，持有区间被截断为
  `[tᵢ, min(tᵢ₊₁, tᵢ + s, horizon))`。截断之后到下一样本（或到新样本重新生效）之间是
  **无效空档**——该通道不满足任何条件：
  - **AND**：空档内该通道无真值，整条规则同步中断；**OR**：空档内仍可由其他通道的有效片段支撑，
    各通道片段按半开区间求交 / 求并，首尾相接仍按连续处理；
  - 空档把真值切成独立片段，**持续时长从每个幸存片段起点重新累计**，
    `confirmed_at = 片段.start + 持续时长`；不足持续时长的片段不成为故障；
  - **故障区间、确认时刻与触发证据都不跨越无效片段**（成立子区间按片段裁剪，证据样本只取片段内）；
  - 通道最后一个样本同样在 `t + s`（或 horizon，取较早者）到期，不再无条件保持到 horizon；
  - 未配置有效期的通道**完全沿用**上面的默认持有语义；有效期只影响该 `(设备, 指标)` 通道，
    与规则无关地作用于所有引用它的条件。
- 条件在其持有的值满足谓词时为真，得到一组 `[start,end)` 半开区间。
- **AND**：所有条件区间求交；某条件对应的通道完全没有数据时，AND 规则永不成立。
- **OR**：各条件区间求并。
- 扫描线只在“合并真值”真正跳变的边界切段，因此
  `[a,b)` 后紧跟 `[b,c)` 这种**边界相接不会产生零长度缝隙**，自动按一段连续区间处理。
- 长度 `end-start ≥ 持续时长` 的真值段才成为故障区间。
- **确认时刻** `confirmed_at = start + 持续时长`（即持续满指定时长的那一刻；时间轴上用 ▴ 标出）。
- 每条故障区间附带**逐条件证据**：该故障内命中的原始样本（event_id / 时间 / 值）与条件成立的子区间。

### 预览影响（不落库的草稿试算）

规则编辑弹层（新建或编辑）里提供 **「预览影响」** 按钮：把当前**未保存草稿**提交到独立的
`POST /api/rules/preview` 接口，服务端分别对以下两份规则做一次**即时试算**，但**不写入**规则表、
故障表或抑制片段表（保存仍完全沿用原来的新建/更新流程）：

- **原规则（baseline）**：编辑场景为库里当前的规则；新建场景为空（无任何原故障）；
- **草稿（draft）**：弹层里尚未保存的名称 / 逻辑 / 持续时长 / 条件。

两侧都使用**当前的遥测事件**与**当前的计划维护窗口**评估（维护窗口照样合并、扣除并重置持续时长；
各通道配置的采样有效期同样生效，到期空档照样切断真值并重置持续时长），草稿与原条件里可选的
**复位阈值**也原样参与试算，
即使故障表里的旧结果相对最新维护/有效期已过期，预览也会自行重算原规则，而不读取过期结果。

两侧的**已确认故障**按**半开区间**逐段比较，返回四类时间片段：

| 片段类型 | 含义 |
| --- | --- |
| `added` 新增片段 | 只被草稿故障覆盖的时间：草稿生效后**新出现**的已确认故障时间 |
| `removed` 消失片段 | 只被原规则故障覆盖的时间：草稿生效后**不再成立**的已确认故障时间 |
| `overlap_changed` 确认时刻变化 | 两侧故障都覆盖的重叠时间，但**确认时刻不同**——即使区间起止完全没变也会标出，片段同时给出两侧确认时刻 |
| `overlap_unchanged` 无变化片段 | 重叠且两侧确认时刻一致（默认折叠，无任何差异时展开并显示「无变化」状态） |

试算后继续编辑草稿，预览结果会标注「已过期，请重新预览」；预览不改变任何数据，确认无误后点
**「保存」**才走原流程（保存后照旧重新评估/刷新）。接口请求体与保存接口相同，另加可选
`rule_id`（省略表示新建预览）；`rule_id` 不存在返回 404。

## 导入批次与撤销

每次文件或文本导入都在 `imports` 表登记一个批次；导入过程中，服务端为该批**首次遇到**的每个
`(device, metric, ts)` 键在 `import_snapshots` 表写一条**导入前快照**：

- 键在导入前不存在：快照 `event_id` 为 `NULL`，撤销时删除该事件（仅当它仍属于本批）；
- 键已存在：快照存档原事件的 `event_id`、`value`、`raw`（原始内容）与 `import_id`（原批次归属），
  撤销时按 id 恢复这三列（仅当事件仍归属本批）；
- 同一批中重复出现的键**只快照第一次遇到前的状态**，但导入仍按原规则由最后一条有效值覆盖；
- 无法解析 / 非数值而跳过的行不产生快照；值为嵌套对象时每个展开出的指标键各自独立快照。

批次列表接口 `GET /api/imports`（页面侧栏「导入批次 / 撤销」卡片）按 id 倒序返回每批的
文件名（文本导入为 `null`）、导入时间、总行数 / 新增 / 覆盖 / 跳过行数、快照键数（其中覆盖键数）、
`snapshot_complete`、`revoked/revoked_at`，以及 `can_undo` 与 `undo_reason`。撤销入口只对满足
以下全部条件的批次开放：

1. **未撤销**（重复撤销返回 409「该导入批次已撤销，不能重复撤销」）；
2. **快照完整**：`snapshot_complete = 1`。升级前创建的旧批次没有快照，页面明确标注
   「旧批次缺少导入前快照，无法撤销」，接口返回 409；
3. **是最近一次未撤销的批次**（后进先出）：更早的批次须先撤销其后的批次，否则返回
   409「仅允许撤销最近一次导入批次，请先撤销其后的导入」。

`POST /api/imports/{id}/undo` 在**单个数据库事务**内依次完成：逐快照删除新增事件 / 恢复被覆盖
事件的值、原始内容与原批次归属（任一快照与当前数据不一致，如目标事件已不属于本批，则抛错并
**整体回滚**，批次不标记撤销）、把该批 `revoked_at` 置为当前时间；事务提交后沿用现有评估流程
`evaluate_all_rules()` 刷新全部故障与被抑制片段（评估失败不影响已提交的数据）。响应为：

```jsonc
{
  "import_id": 2,
  "deleted_events": 1,          // 本批新增、被删除的事件数
  "restored_events": 1,         // 被本批覆盖、恢复原值的事件数
  "evaluation": { "rules_evaluated": 3, "fault_intervals": 4, "suppressed_segments": 0 }
}
```

撤销保留批次行与快照（标记「已撤销」用于审计展示）；**清空数据**（`POST /api/reset`）会
连同 `import_snapshots` 与 `imports` 一并清空。老版本数据库首次启动时自动加列迁移
（`imports.snapshot_complete` 默认 0、`revoked_at`、`overwritten_rows`）并创建快照表，
旧批次因此被明确拒绝撤销而不是被静默按空快照处理。

## 计划维护

维护窗口是**按设备**命名的半开区间 `[start, end)`，在「计划维护」卡片或时间轴拖拽框选中创建，
可编辑、删除；每次写入后服务端**自动重新评估全部规则**（无需再手动点「评估规则」）。评估语义：

1. **合并**：同一设备上重叠或首尾相接的维护窗口先合并为最大连续维护段（不同设备互不合并）。
2. **扣除**：把该设备每个条件通道的成立区间减去维护段，再做 AND/OR 合并——
   即维护只影响**该设备参与**的规则，其他设备的通道与规则不受影响。
3. **重置持续时长**：维护段把真值段切成独立片段，持续时长从每个幸存片段的起点**重新累计**，
   `confirmed_at = 片段.start + 持续时长`；不足持续时长的片段不再成为故障，
   因此故障列表只保留**扣除后达标**的区间。
4. **证据不越界**：触发证据的成立子区间与命中样本都按扣除后的区间裁剪，
   不会越过维护边界（维护窗口内不会出现证据样本）。
5. **被抑制片段**：规则真值因维护而丢失的部分（扣除前真值 − 扣除后真值，落在维护段内）
   逐条件通道记录为被抑制片段，携带关联规则与来源维护窗口；
   时间轴上以琥珀色斜纹显示在对应通道泳道顶部，并随导出 JSON 输出。

时间轴上维护同时以两种形式呈现：顶部青色**维护带**（`设备 · 名称`，重叠窗口自动分行）和
该设备每个泳道内的**维护底色**；维护带、被抑制片段、故障色块都支持悬停查看详情。

## 采样有效期（TTL）

有效期按 **`(设备, 指标)` 通道**配置，值为**正秒数**（不允许 0 / 负数 / 非数字）；在左侧
「采样有效期」卡片查看、设置、编辑、清除，也可通过 API 操作。配置可先于数据存在：为尚未导入
的通道设置有效期不报错，数据导入后立即按该有效期评估。语义要点：

1. **截断持有**：样本 `(tᵢ, vᵢ)` 只在 `[tᵢ, min(tᵢ₊₁, tᵢ + s, horizon))` 内保持其值；其后到下一样本
   之间（或末样本 `tᵢ + s` 之后）为无效空档，谓词不成立、不产生持有区间。
2. **AND/OR 组合**：空档只切断本通道条件；AND 在空档内整体不成立，OR 仍可由其他通道的有效片段
   覆盖。不同通道有效片段照常做半开求交 / 求并，`[a,b)` 与 `[b,c)` 相接仍按连续处理。
3. **持续时长重新累计**：真值被空档切断后，每个幸存片段独立按 `end-start ≥ 持续时长` 判定，
   `confirmed_at = 片段.start + 持续时长`；不足时长的片段不产生故障。
4. **证据不越界**：故障区间、确认时刻、成立子区间与命中样本全部按有效片段裁剪，
   不会跨过到期空档（也不会跨过维护窗口）。
5. **变更即重算**：设置、修改或清除有效期后服务端**自动重新评估全部规则**；计划维护继续参与
   评估（空档与维护窗口都会切断真值，被维护扣除的片段仍单独记为被抑制片段，到期空档本身不计为
   维护抑制）。
6. **补传旧样本后重算**：导入事件（含时间更早的补传、对旧时间点的后值覆盖）后同样自动重算已存
   故障——补传可能把原本到期的空档桥接起来，也可能覆盖旧值改变谓词结果。
7. **未配置不变**：没有有效期配置的通道与历史行为完全一致（保持到下一样本 / 末样本到 horizon）。

时间轴上，配置了有效期的通道泳道左上角显示紫色 **⏳ 有效期** 徽标（悬停查看语义）；有效期列表
在左侧卡片，随导出 JSON 的 `channel_ttls` 字段一并输出。

## 时间范围筛选语义

- 原始事件是时间点，筛选时**两端包含**（`start ≤ ts ≤ end`）。
- 故障区间 / 标注 / 维护窗口 / 被抑制片段是 `[start,end)` 半开区间，与筛选窗口按**半开相交**返回
  （`iv.end > start AND iv.start < end`）。
- 筛选同时作用于时间轴、故障列表、故障事件列表、标注列表、维护窗口列表、原始事件表和导出。

## 故障事件归并语义

「故障事件」是**只读派生视图**，不改写、不删除 `fault_intervals` 中的任何原始故障结果：

- 两条故障（通常来自**不同规则**）的半开区间**重叠**或**首尾相接**（`[a,b)` 与 `[b,c)`）即属于同一事件；
  该关系按**传递闭包**归并——A 接 B、B 接 C，则 `{A,B,C}` 同属一个事件，即使 A、C 本身不相交。
  归并在全部故障上先完成，再套用时间筛选，因此跨窗口的传递链不会被截断。
- 事件区间 = 成员故障的**最早开始**至**最晚结束**，并列出每个成员的规则、各自 `[start,end)`
  区间、确认时刻和**原触发证据**（条件成立子区间与命中样本，逐字取自原故障）。
- 事件列表沿用当前时间范围：事件整体与筛选窗口半开相交即出现；仅在窗口外的成员仍会列出，
  以「窗口外」标签和淡化色块标出（`in_window: false`）。
- 同一规则自身相邻的故障区间在扫描线评估时已按相接合并，因此事件归并天然发生在不同规则之间。

## 规则组合故障日账（只读）

在「规则组合故障日账」卡片勾选**一组规则**、填写查询时间范围（本机时区输入，按 UTC 查询），即得到
该组合在 `[start, end)` 内逐日（UTC）的故障统计。对应只读接口 `GET /api/fault-daily-ledger`。
计算规则：

1. **读取已确认结果**：只取选中规则在 `fault_intervals` 表里**已保存的故障区间**（含维护扣除、
   有效期截断、持续时长过滤后的结果）。日账不评估、不重算任何规则；导入事件、编辑规则、变更
   采样有效期 / 维护窗口触发的重算仍完全走现有流程。
2. **半开合并去重**：选中规则的所有区间先按 `[start, end)` 合并——重叠或首尾相接
   （`[a,b)` 与 `[b,c)`）都并为一段。于是同一时刻即使被多条规则判为故障，故障秒数也**只计一次**。
3. **按 UTC 午夜切分**：合并后的片段在每个 **UTC 00:00** 边界切开，落到各自的 UTC 日；
   查询窗口覆盖到的每一天都出现在结果中（包括零故障的日子，覆盖率为 0）。
4. **逐日指标**：
   - `fault_seconds` 去重故障秒数：当日落在查询窗口内的合并故障总秒数；
   - `new_segments` 新起片段数：片段**起始时刻所在的 UTC 日**计为新起，一段只计一次；
   - `continuing_segments` 跨日延续片段数：片段起始于更早的 UTC 日、跨过午夜延续到当日；
   - `queried_seconds` 当日实际查询秒数：整日为 86400；查询首尾落在日中时，首尾两日按
     `[max(日界, start), min(次日界, end))` 裁剪；
   - `coverage` 故障覆盖率 = `fault_seconds / queried_seconds`，始终在 `[0, 1]`。
5. **边界约定**：片段**恰在午夜结束**时（半开 `[..., 午夜)`）不进入次日，次日既不计故障秒数也
   不计延续；片段恰在午夜开始时在当日计新起；片段在查询起点之前已开始时，起点所在日仍按其
   真实起始 UTC 日判定新起 / 延续。

响应同时给出选中规则（id / 名称）、查询范围、合并后的半开片段列表 `merged_segments`、逐日 `days`
以及合计 `totals`（总故障秒数、总查询秒数、新起 / 延续总数、合并片段数、总覆盖率）。
页面卡片上方展示**选中规则**与**查询范围**，下方为逐日表格（UTC 日期 / 当日查询秒数 /
去重故障秒数 / 新起片段 / 跨日延续 / 覆盖率，末行为合计）。

## HTTP API 摘要

| 方法 & 路径 | 说明 |
| --- | --- |
| `GET /api/health` | 健康检查 |
| `GET /api/meta` | 运算符、数据时间范围与计数 |
| `POST /api/import` | multipart 上传 JSONL（字段：`file`，可选 `device_field/metric_field/ts_field/value_field`）；导入后自动重新评估全部规则（补传旧样本同样重算），响应带 `evaluation` 摘要 |
| `POST /api/import/text` | 直接提交 JSONL 文本（JSON body：`{text, ...字段映射}`）；导入时为本批首次遇到的每个（设备、指标、时间戳）记录导入前快照，导入后同样自动重算 |
| `GET /api/imports` | 导入批次列表（最新在前）：行数统计、快照键数、`snapshot_complete`、`revoked/revoked_at`、`can_undo` 与不可撤销原因 `undo_reason` |
| `POST /api/imports/{id}/undo` | **撤销导入批次**：仅最近一次未撤销且快照完整的批次可撤销；同一事务删除本批新增事件、恢复被覆盖事件的值/原始内容/原批次归属、标记已撤销，失败全部回滚；成功后自动重算故障并返回 `deleted_events` / `restored_events` / `evaluation`。批次不存在 404；已撤销、非最近批次或旧批次无快照返回 409 |
| `GET /api/channels` | 通道列表及值范围 |
| `GET /api/channel-ttls?device&metric` | 各通道采样有效期（正秒数；未列出的通道沿用默认持有语义） |
| `PUT /api/channel-ttls` | 设置/修改某通道有效期（body：`device`、`metric`、`ttl_seconds>0`），保存后自动重新评估全部规则并返回评估摘要 |
| `DELETE /api/channel-ttls?device&metric` | 清除某通道有效期（恢复默认语义并自动重算；未配置返回 404） |
| `GET /api/events?start&end&device&metric&limit&offset` | 原始事件（时间含端点，分页） |
| `GET/POST /api/rules`，`GET/PUT/DELETE /api/rules/{id}` | 规则增删改查；条件可带可选 `reset_threshold`（仅 `>`、`>=`、`<`、`<=`，高值触发须低于触发阈值、低值触发须高于，否则 400；省略或 `null` 表示不设置，沿用原比较） |
| `POST /api/rules/preview` | **预览影响**：未保存草稿与原规则分别按当前事件+计划维护+采样有效期即时试算（草稿条件中的 `reset_threshold` 同样生效），半开区间比较已确认故障，返回新增/消失/确认时刻变化/无变化片段；不写入任何表（body 同规则保存，可选 `rule_id`） |
| `POST /api/evaluate` | 重新评估全部规则，重算故障区间与证据 |
| `GET /api/faults?start&end` | 故障区间（含证据，半开相交筛选；已扣除维护） |
| `GET /api/fault-events?start&end` | 故障事件：跨规则重叠/首尾相接（传递）归并，含成员故障与原证据 |
| `GET /api/fault-daily-ledger?rules&rules&start&end` | **规则组合故障日账（只读）**：合并选中规则的已保存故障（重叠/相接去重），按 UTC 午夜切分，逐日返回去重故障秒数 / 新起片段 / 跨日延续 / 当日查询秒数 / 覆盖率及合计；未知规则 404、空或倒置范围 400/422 |
| `GET/POST /api/maintenance`，`GET/PUT/DELETE /api/maintenance/{id}` | 计划维护窗口增删改查（按设备、半开区间；写入后自动重新评估全部规则并返回评估摘要） |
| `GET /api/suppressed?start&end` | 被维护抑制的片段（关联规则与来源维护窗口，半开相交筛选） |
| `GET/POST /api/annotations`，`DELETE /api/annotations/{id}` | 区间标注 |
| `GET /api/timeline?start&end&max_points` | 时间轴聚合数据（通道抽样、故障、维护窗口、被抑制片段、标注） |
| `GET /api/export?start&end&download=true` | 导出完整 JSON（附件下载，含维护窗口与被抑制片段） |
| `POST /api/demo` | 载入内置示例数据与规则（同样记录批次快照，可在「导入批次」中撤销） |
| `POST /api/reset` | 清空全部数据（事件、规则、故障、维护、标注，以及导入批次与导入前快照） |

时间参数均可使用 ISO-8601 或 epoch 数字。完整交互模式见 http://localhost:8000/docs 。
